# Architecture Checklist

**Цель**: Отслеживание прогресса при выполнении `/plan-feature`.

**Как использовать**: Отмечай ✅ после завершения каждого пункта.

---

## Pre-Planning

- [ ] Фича выбрана из `features-registry.md`
- [ ] Загружен контекст (Acceptance Criteria, motivation, impact, dependencies)
- [ ] Понятны бизнес-требования
- [ ] Загружен существующий `architecture.md` (если есть)

---

## Phase 1: Problem Analysis

- [ ] Проблема четко сформулирована (что, почему, кто)
- [ ] Показано текущее состояние (as-is)
- [ ] Показано желаемое состояние (to-be)
- [ ] Объяснено, почему это сложно (технические вызовы)
- [ ] Заданы уточняющие вопросы (через AskUserQuestion)
- [ ] Раздел "1. Problem Analysis" добавлен в `architecture.md`
- [ ] ✅ **УТВЕРЖДЕНО пользователем**

---

## Phase 2: Alternatives Analysis

- [ ] Перечислены все возможные подходы (минимум 2-3)
- [ ] Сравнение по критериям (сложность, риски, time-to-market, maintenance)
- [ ] Рекомендован лучший вариант с обоснованием
- [ ] Показаны trade-offs
- [ ] Оформлен ADR-XXX
- [ ] Раздел "2. Alternatives Analysis" добавлен
- [ ] ✅ **УТВЕРЖДЕНО пользователем**

---

## Phase 3: User Scenarios

- [ ] Описаны ВСЕ сценарии (happy path + alternatives + edge cases)
- [ ] Для каждого сценария показаны:
  - [ ] Preconditions
  - [ ] User actions
  - [ ] **System internals** (компоненты, API calls, DB queries, state updates)
  - [ ] Postconditions
- [ ] Минимум 3-5 детальных сценариев
- [ ] Dataflow для каждого сценария понятен
- [ ] Раздел "3. User Scenarios" добавлен
- [ ] ✅ **УТВЕРЖДЕНО пользователем**

---

## Phase 4: Dataflow Diagram

- [ ] Детальный поток данных через всю систему
- [ ] Все точки взаимодействия показаны (User → Frontend → Backend → Services → DB)
- [ ] Формат данных указан на каждом этапе
- [ ] Трансформации данных показаны
- [ ] Mermaid diagram создан
- [ ] Раздел "4. Dataflow Diagram" добавлен
- [ ] ✅ **УТВЕРЖДЕНО пользователем**

---

## Phase 5: Component Interaction

- [ ] Перечислены ВСЕ компоненты системы (включая external)
- [ ] Показано, кто кого вызывает (call graph)
- [ ] Интерфейсы взаимодействия определены (типы параметров и возврата)
- [ ] Направление зависимостей показано
- [ ] Dependency graph создан (Mermaid)
- [ ] Раздел "5. Component Interaction" добавлен
- [ ] ✅ **УТВЕРЖДЕНО пользователем**

---

## Phase 6: Edge Cases

- [ ] Перечислены ВСЕ edge cases:
  - [ ] Ошибки пользователя
  - [ ] Ошибки системы
  - [ ] Граничные условия
  - [ ] Concurrent operations
- [ ] Для каждого edge case указано:
  - [ ] Вероятность
  - [ ] Влияние
  - [ ] Обработка
  - [ ] Где реализовано
- [ ] Определены acceptable failures (для MVP)
- [ ] Раздел "6. Edge Cases" добавлен
- [ ] ✅ **УТВЕРЖДЕНО пользователем**

---

## Phase 7: Type Contracts

- [ ] Public API определен (что видит клиент)
- [ ] Internal State определен (что хранится внутри)
- [ ] Component Interfaces определены (границы между компонентами)
- [ ] Все типы в TypeScript/Zod формате
- [ ] Указано, какие поля обязательные, какие опциональные
- [ ] Раздел "7. Type Contracts" добавлен
- [ ] ✅ **УТВЕРЖДЕНО пользователем**

---

## Phase 8: Risks & Mitigations

- [ ] Идентифицированы все технические риски:
  - [ ] Архитектурные
  - [ ] Технологические
  - [ ] Интеграционные
  - [ ] Performance
- [ ] Для каждого риска указано:
  - [ ] Вероятность (LOW/MEDIUM/HIGH)
  - [ ] Влияние (LOW/MEDIUM/HIGH/CRITICAL)
  - [ ] Митигация
  - [ ] Owner
- [ ] Определены критичные риски (требуют внимания)
- [ ] Определены acceptable risks (для MVP)
- [ ] Раздел "8. Risks & Mitigations" добавлен
- [ ] ✅ **УТВЕРЖДЕНО пользователем**

---

## Phase 9: Implementation Plan

- [ ] Фича разбита на конкретные задачи
- [ ] Definition of Done определен для каждой задачи
- [ ] Сроки оценены (недели/дни)
- [ ] Порядок реализации определен (dependencies между задачами)
- [ ] Критерии готовности указаны (тесты, метрики)
- [ ] **TodoList создан через TodoWrite**
- [ ] Раздел "9. Implementation Plan" добавлен
- [ ] ✅ **УТВЕРЖДЕНО пользователем**

---

  - [ ] Протоколы

  - [ ] Ключевые сценарии
