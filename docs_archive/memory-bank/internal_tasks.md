# WayMates — Анализ роста по 3 осям (Breadth / Depth / Ownership)

_Краткий, целостный контекст из обсуждения. Готово под разработку UI и бэкенда._

## Задумка
Мы отображаем **рост человека во времени** по трём процессным осям и **сопоставляем** его с эталонными «ролевыми профилями» (на старте — _Tech Lead_ и _Team Lead_). Повышения грейда/роли считаются **внешними событиями признания** (recognition events) и служат контрольной точкой: «на каких сочетаниях осей обычно происходило признание».

Идея — **быстро видеть**:
- где человек **усиливается** (какая ось тянет вверх);
- где есть **узкое горлышко** (ось с плато/отставанием);
- к какому **ролевому треку** ближе текущий состав усилий;
- **сколько обычно** не хватает по каждой оси до следующего шага (грейда/роли) — через эталоны.

## Оси и смысловые единицы
- **Breadth (широта доменной области):** разнообразие поддоменов/задач, «мостиковые» активности (DevOps, тесты, аналитика), энтропия доменных тегов, разношёрстные стеки.
- **Depth (глубина доменной области):** сложность задач, архитектурные решения, оптимизации, инциденты L3+, дизайн, владение внутренними примитивами/алгоритмами.
- **Ownership (теневое лидерство/ответственность):** ведение задач от идеи до продакшена, авторство RFC/ADR, пост‑мортемы, менторство, координация межкомандных задач, on‑call leadership.

> Все оси — **кумулятивные 0–100** (прогресс не убывает, при паузах линия продолжается с того же уровня).

## Сырые сигналы → Снапшоты
1. **Сырые события**: PR/мерджи, релизы, инциденты, роли в проектах, доклады/доки, учебные эпизоды и т.п.  
2. **Фичи осей**: маппим событие в вклад по одной или нескольким осям (дельта уровня).  
3. **Снапшоты**: агрегируем дельты в кумулятивные ряды `level(t)` для каждой оси; считаем производные:
   - `vel_30/90` — прирост за 30/90 дней;
   - `accel_90` — ускорение.
4. **Нормализация**: 0–100 по когорте/домейну/уровню.



## Признание (recognition events)
- События: `grade` (повышение грейда), `role` (изменение роли/скоупа).
- Используются как контрольные точки: на **каких значениях/темпах** осей обычно происходило признание в когорте.

## «Паттерны треков» (интерпретация для пользователя)
- **Тех‑трек** (_Tech Lead → Architect_): интенсивный и устойчивый рост **Breadth+Depth**, достаточная **Ownership**.
- **Менеджерский трек** (_Team Lead → PM_): выраженный рост **Ownership**, при достаточных B/D.
- Это видно на «составе» эталонов: у _Tech Lead_ доли B/D выше, у _Team Lead_ — выше доля Ownership.

## Где «тормозит» рост (детектор плато/отставания)
- **Плато**: прирост `< ε` (например, <2 баллов) за окно `W` (например, 12 недель) по оси.
- **Отставание**: время достижения T20/T50 значительно позже p90 когорты.
- **Дисбаланс**: B ≫ D или наоборот при типичном лаге; низкий Ownership при достаточной D.
- В UI: подсветка проблемной оси и «ожидаемой зоны» (когортный коридор).


## MVP → прод
- MVP: stacked‑area + 2 эталона (Tech Lead, Team Lead), события признаний, базовый детектор плато.
- Prod: когорты в разрезах доменов, p25/p50/p75 в эталонах, алерты «к чему ближе», рекомендации по интервенциям.

# WayMates: Архитектура задач (Tasks Architecture)

**Дата:** 20 сентября 2025  
**Статус:** Архитектурные решения  
**Тема:** Полная архитектура системы задач для внутреннего развития навыков

---

## 🎯 Концепция задач

### **Что такое задача:**
Задача — это **должностная обязанность в компании**, которая развивает навыки и влияет на рост по осям Breadth/Depth/Ownership.

### **Ключевые принципы:**
- **Должностные обязанности** - рабочие задачи в компании
- **Измеримый вклад** - влияние на рост по осям
- **Источник опыта** - что делал аватар для достижения цели
- **Внутренний рост** - развитие внутри фирмы

---
Можно добавить свою бизнес-логику — нормализовывать все задачи пользователя по направлению вектора (по схожести стека) — оценить через глубину вектора суть схожих по стеку задач пользователей — давать AI результаты, чтобы он подводил итоги → сложно, но возможно. **Дальше даем рекомендации


## 🏗️ Структура данных задачи

### **Основные поля:**
```yaml
task:
  task_id: "task_1"
  task_name: "Архитектурный проект микросервисов"
  description: "Вел архитектурный проект микросервисов"
  project_context: "E-commerce platform"
  duration_months: 6
  
  # Навыки (храним)
  skills_developed: ["microservices", "architecture", "leadership"]
  onet_skills: ["systems_analysis", "project_management"]
  
  # Метаданные
  avatar_id: "avatar_1"
  completion_date: "2024-06-15"
  verification_status: "verified"
  
  # axes_impact вычисляем на лету, не храним
```

### **Вычисляемые поля:**
```yaml
calculated_fields:
  axes_impact:
    breadth: 20    # Работал с разными сервисами
    depth: 30      # Глубокие архитектурные решения
    ownership: 25  # Вел проект от идеи до продакшена
```

## 🗄️ Хранение задач

### **1. Neo4j (графовая структура):**

**Узлы и связи:**
- `(Avatar)-[:COMPLETED_TASK]->(Task)` - аватар выполнил задачу
- `(Task)-[:DEVELOPS_SKILL]->(Skill)` - задача развивает навык
- `(Task)-[:IN_PROJECT]->(Project)` - задача в рамках проекта

**Свойства узла Task:**
- Основные данные: `task_name`, `description`, `project_context`
- Навыки: `skills_developed[]`, `onet_skills[]`
- Метаданные: `avatar_id`, `completion_date`, `verification_status`

### **2. S3 (полные данные):**
- Детальные описания задач
- Доказательства выполнения
- Логи AI анализа

---

## 🔍 Использование задач

### **1. Показ внутреннего роста аватара:**
- **После построения маршрута** - какие задачи выполнял аватар
- **Рост по осям** - как задачи влияли на развитие
- **Временная привязка** - когда какие задачи делал

### **2. Мониторинг прогресса пользователя:**
- **Сравнение с аватаром** - на том же этапе развития
- **Фокус на осях** - какие задачи нужны для роста
- **Рекомендации** - что делать дальше

### **3. Вычисление осей пользователя:**
- **Динамический расчет** - на основе выполненных задач
- **Сравнение с аватаром** - только после выбора аватара
- **Уведомления** - при отставании от аватара

---

## 🔧 Data Pipeline для задач

### **1. Сбор данных:**
- **От аватаров** - исторические задачи с результатами
- **От пользователей** - текущие задачи с метриками
- **Автоматический сбор** - из корпоративных систем

### **2. Обработка AI:**
- **Анализ описания** - AI понимает что делал пользователь
- **Расчет осей** - AI определяет вклад в Breadth/Depth/Ownership
- **Извлечение навыков** - AI извлекает развиваемые навыки
- **O*NET маппинг** - сопоставление с O*NET таксономией

### **3. Валидация:**
- **Проверка осей** - корректность расчета
- **Проверка навыков** - корректность извлечения
- **Верификация** - подтверждение от коллег/менеджеров

### **4. Сохранение:**
- **Neo4j** - структурированные данные + связи
- **S3** - полные описания + доказательства
- **Индексация** - создание индексов для поиска

## 🔍 Алгоритмы работы с задачами

### **1. Вычисление осей пользователя:**
```yaml
calculate_user_axes:
  input: "Список задач пользователя по дате"
  algorithm: "Суммируем axes_impact всех задач"
  output: "Текущие значения [breadth, depth, ownership]"
```

### **2. Сравнение с аватаром:**
```yaml
compare_with_avatar:
  input: "Оси пользователя + оси аватара на том же этапе"
  algorithm: "Вычисляем разности и отклонения"
  output: "Гапы, уведомления, рекомендации"
```

### **3. Мониторинг прогресса:**
```yaml
monitor_progress:
  trigger: "После выбора аватара"
  steps:
    - "Вычислить текущие оси пользователя"
    - "Получить оси аватара на том же этапе"
    - "Сравнить и показать раскладку"
    - "Сгенерировать рекомендации по фокусу"
```
