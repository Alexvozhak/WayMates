## 🎯 Концепция троп

### **Что такое тропа (Trail):**
Тропа — это **проверенный путь внешнего развития навыков** между двумя контекстами пользователя.

### **Ключевые принципы:**
- **Проверенность:** Путь подтвержден несколькими людьми
- **Внешнее развитие:** Изучение навыков за пределами компании
- **Агрегированные метрики:** Средние значения по всем верификаторам
- **Неизменяемость:** Тропы не редактируются после подтверждения. В течение холодного старта у него есть ещё 10 дней на редактирование, а после создания нового контекста пользователя все истории (тропы) фиксируются как есть. После холодного старта редактировать опубликованные истории станет нельзяТо есть до фиксации нового контекста история не опубликовывается и не фиксируется, можно её редактировать пока что.

### **После AI нормализации (генерация ключа и связывание):**
- Вход проходит AJV-валидацию по схеме
- Если не проходит или семантика неоднозначна - AI доуточняет у пользователя и дописывает
- Создание/проверка в Neo4j через Cypher:
```cypher
MATCH (t:Trail {trail_id: "var1"})

MERGE (spn:SkillPlatformNode {skill: LOWER(t.skill), platform: LOWER(t.platform)})
```
- Связывает Trail [:PART_OF]-> spn

### **SkillPlatformNode в Neo4j:**
SkillPlatformNode — группирующий узел в Neo4j с ключом (skill + platform), создаётся/проверяется через Cypher.



### **Расчёт метрик (на лету в Cypher):**
```cypher
MATCH (spn:SkillPlatformNode {skill: "typescript", platform: "udemy"})
MATCH (t:Trail)-[:PART_OF]->(spn)

WITH count(t) AS trail_count,  // Переименовано, т.к. без верификации
     avg(t.cost_usd) AS avg_cost_usd,
     avg(t.rating_course) AS avg_rating_course,
     avg(t.rating_platform) AS avg_rating_platform,
     collect({
       total_duration_weeks: t.total_duration_weeks,
       schedule: t.schedule,
       rating_schedule: t.rating_schedule,  // Если есть
       user_feedback: t.user_feedback
     }) AS all_details

RETURN trail_count, avg_cost_usd, avg_rating_course, avg_rating_platform, all_details
# Актуальный расчёт с коллекциями для деталей (после изменений)
```

## 🔧 Data Pipeline для троп

### **AI Normalization:**
- Вход: сырой JSON с полями skill и platform (после AJV-валидации)
- Шаги:
  1. Нормализовать: lowercase, обработать синонимы (с помощью AI промта)
  2. Cypher: MERGE (spn:SkillPlatformNode {skill: normalized_skill, platform: normalized_platform})  // Создаёт/находит по композитному ключу
  3. Создать Trail с нормализованными данными (trail_id, user_id, total_duration_weeks, schedule, etc.)
  4. Связать: MERGE (t:Trail {trail_id: new_id})-[:PART_OF]->(spn)
  5. Если нужно, обновить метрики на лету (через отдельный запрос)
- Выход: trail_id, связанное с skill_platform_node

## 🗄️ Хранение троп

### **1. Neo4j (графовая структура):**

**Узлы и связи:**
- (Platform {name: "udemy"})  # Узел платформы (утверждено, lowercase)
- (SkillPlatformNode {skill: "typescript", platform: "udemy"})  # Группирующий узел по композитному ключу
- (Trail {trail_id: "var1", ...})  # Индивидуальная тропа
- Связи:
  - (SkillPlatformNode)-[:ON_PLATFORM]->(Platform)  # Агрегат привязан к платформе
  - (Trail)-[:PART_OF]->(SkillPlatformNode)  # Тропы связываются с агрегатом
  - (SkillPlatformNode)-[:DEVELOPS_SKILL]->(Skill {name: "typescript"})  # Опционально, если есть отдельный узел навыка (утверждено, если нужно)

**Свойства:** Только ключи и статичные данные; метрики не хранятся (рассчитываются на лету, утверждено)

## 🔍 Поиск и использование троп

### Архитектурный подход (только KAG)
**Контекстно‑зависимый подход:** сравнение по текущему контексту (последний открытый период). Прошлые контексты могут учитываться как мягкий фолбек (недавние навыки) при недостатке результатов.

Публикация троп при закрытии контекста:
- При закрытии контекста пользователь выбирает одну или несколько причин `transition_types[]`: promotion | demotion | role_change | employer_change | tech_stack_change | relocation | planned | custom.
- Можно добавить комментарий `transition_note` и оценки периода: satisfaction_overall (1–5), trails_helpfulness (1–5), feedback (текст).
- Тропы текущего периода приводятся в порядок и фиксируются вместе с контекстом; в новый контекст переносятся только реально используемые навыки.

### Ключевые инсайты
- Простота и объяснимость: матч по текущему контексту.
- Честность: не переоцениваем «багаж» прошлых стеков.
- Расширение поиска: при нехватке результатов допускаем учёт последнего закрытого контекста с пониженными весами.

### Наши допущения
- По умолчанию берём только текущий контекст; история — опциональный фолбек.
- Навыки переносятся в новый контекст только если реально используются.
- Простая формула достаточна для MVP.

### **Алгоритм поиска (MVP):**
1. MATCH по композитному ключу {skill, platform}
2. Фильтрация троп (Trail) по constraints (время, бюджет, deadline)
3. Scoring через веса: matchedSkills + platformRating + costCompatibility + timelineCompatibility
4. Возврат отсортированных троп по убыванию score
5. **Отложено:** Векторизация для семантического поиска

### **Типы поиска (MVP):**
- По навыкам (e.g., все тропы для "typescript")
- Построение маршрутов (e.g., цепочка троп для карьерного роста)
- Фильтрация по constraints (e.g., cost_usd < 200, hours_per_week <= 10)
- Аналитика по ресурсам (e.g., avg_rating_platform для "udemy")
- Статистика по навыкам (e.g., avg_total_duration_weeks)
- **Отложено:** Семантический поиск по описаниям троп

## MVP (Этап 1): Упрощенный подход без векторизации

### Принципы MVP:
- **Граф + AI нормализация:** Структурированные данные через TypeBox схемы
- **Constraints фильтрация:** Время, бюджет, deadline через простые проверки  
- **Scoring через веса:** Единый подход без категорий (как в когорте)
- **Простота:** Constraints покрывают 90% случаев, enum'ы не нужны

### Отложено до post-MVP:
- Векторизация троп для семантического поиска
- Сложные AI рекомендации
- Категоризация результатов
