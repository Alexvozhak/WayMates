# 🧪 Промпт для создания тестов search-modes модулей

## 📋 **Контекст проекта**
- **Проект:** WayMates - платформа поиска карьерных переходов
- **Стек:** Neo4j + Zod + Vitest
- **Архитектура:** search-modes модули выполняют Cypher запросы через Neo4j driver
- **Текущее состояние:** Есть только интеграционные тесты, unit тестов НЕТ

## 🎯 **Задача**
Создать полноценное покрытие тестами для модулей `src/search-modes/`:
- `current-only.ts` - анализ развития текущего контекста
- `current-to-target.ts` - поиск переходов от текущего к целевому
- `target-only.ts` - анализ карьерных путей к целевой роли  
- `target-search.ts` - поиск пользователей по целевому контексту
- `helpers.ts` - вспомогательные функции

## 🏗️ **Архитектурные ограничения**

### **Стиль кода:**
- Использовать существующие импорты из `../helpers/test-data-loader.js`
- Следовать паттернам из `tests/unit/scoring.test.ts` и `tests/unit/upsert-story.test.ts`
- Использовать Vitest (`describe`, `test`, `expect`, `vi`)
- НЕ создавать новые helper функции без необходимости

### **Структура файлов:**
- Unit тесты: `tests/unit/search-modes/[module-name].test.ts`
- Интеграционные тесты: дополнить `tests/integration/mcp-tools.test.ts`
- Функциональные тесты: дополнить `tests/functional/mcp-workflows.test.ts`

### **Зависимости:**
- НЕ добавлять новые npm пакеты
- Использовать существующие моки и утилиты
- Переиспользовать `loadTestData()` из test-data-loader

## 🧪 **Требования по типам тестов**

### **Unit тесты (`tests/unit/search-modes/`):**
**Что тестировать:**
- Валидацию входных параметров через Zod схемы
- Обработку edge cases (пустые массивы, undefined значения)
- Корректность вызовов helper функций (`getStrictSkills`, `getValidatedTypes`)
- Формирование cypherParams объектов
- Обработку ошибок валидации

**Подход:**
- Мокать Neo4j driver полностью
- Мокать `runQuery` и `getValidatedTypes` из helpers
- Тестировать изолированно бизнес-логику
- Быстрые тесты (< 100ms каждый)

**НЕ тестировать:**
- Реальные Cypher запросы (это интеграционные тесты)
- Neo4j результаты (мокать)
- Производительность БД

### **Интеграционные тесты (дополнить existing):**
**Что тестировать:**
- Полный цикл выполнения с реальной Neo4j БД
- Корректность Cypher запросов из `SearchQueries`
- Валидацию результатов через Zod схемы
- Производительность запросов (< 5 секунд)

**Использовать:**
- Существующую БД инфраструктуру из `database-setup.ts`
- Реальные тестовые данные из `loadTestData()`
- Существующие паттерны из `database-operations.test.ts`

### **Функциональные тесты (улучшить existing):**
**Проблема:** Текущие MCP тесты нечитаемы и сложны для восприятия

**Что улучшить:**
- **Читаемость:** Разбить сложные тесты на простые, понятные сценарии
- **Структура:** Четкое разделение setup → action → assertion
- **Названия:** Описательные имена тестов, отражающие бизнес-сценарий
- **Документация:** Комментарии на русском для сложной логики
- **Данные:** Использовать минимальные, понятные тестовые данные

**Что тестировать:**
- Workflow сценарии через MCP server (упрощенные)
- Комбинации search-modes (по одному сценарию)
- Валидацию бизнес-сценариев (фокус на happy path)

**Использовать:**
- Реальные тестовые данные из `loadTestData()`
- Принципы: KISS, DRY, читаемость > краткость

## 📊 **Тестовые кейсы по модулям**

### **helpers.ts:**
- `runQuery`: моки driver/session, обработка ошибок подключения
- `getValidatedTypes`: валидация схем, обработка невалидных данных
- `getStrictSkills`: фильтрация по категориям, обработка undefined/empty

### **current-only.ts:**
- Валидация `CurrentOnlyParams`
- Обработка `lookAheadMonths` (граничные значения)
- Формирование `strictSkills` и `cypherParams`
- Обработка `reasonsToTrack` и `searchConstraints` по умолчанию

### **current-to-target.ts:**
- Валидация `CurrentToTargetParams`
- Обработка `currentContext` и `targetContext`
- Формирование `strictSkills`
- Валидация результата через `CurrentToTargetResultSchema`

### **target-only.ts:**
- Валидация `TargetOnlyParams`
- Обработка случая "No target contexts found"
- Возврат единственного агрегированного результата
- Валидация через `TargetAnalysisResultSchema`

### **target-search.ts:**
- Валидация `TargetSearchParams`
- Обработка `searchConstraints` по умолчанию
- Валидация массива результатов через `AvatarSearchResultSchema`

## 🔍 **Анализ и аудит продакшн кода (ОБЯЗАТЕЛЬНО)**

### **Этап 1: Reverse Engineering**
- Изучить `tests/functional/mcp-workflows.test.ts` для понимания реальных ожиданий
- **Проблема:** Текущие тесты нечитаемы - нужно упростить и структурировать
- Проследить путь: MCP tool → search-mode → Cypher → результат  
- Выявить расхождения между документированным и фактическим поведением
- Понять бизнес-логику каждого search-mode через существующие рабочие тесты
- **Цель:** Создать читаемые, понятные тесты вместо сложных монолитных

### **Этап 2: Cypher Quality Audit**
- **Бизнес-логика:** Соответствует ли запрос ожидаемой функциональности?
- **Производительность:** Нужны ли дополнительные индексы? Оптимальны ли пути в графе?
- **Edge cases:** Обрабатывает ли пустые результаты, дубликаты, некорректные данные?
- **Валидация:** Правильные ли фильтры, JOIN'ы, агрегации?

### **Этап 3: Context7 Integration**
- При сложных Cypher запросах - автоматически запрашивать Neo4j документацию
- Валидировать синтаксис и best practices через Context7
- Создать отдельный файл `CYPHER_AUDIT_RECOMMENDATIONS.md` с найденными проблемами

### **Этап 4: Честное тестирование**
- **НЕ подыгрывать коду:** Если тест падает - анализировать причину, НЕ менять ожидания
- **Тестировать бизнес-логику:** А не текущую реализацию
- **Стратегия исправлений:**
  1. Если очевидно - исправляй Cypher сам
  2. Есть сомнения - пробуй Context7, делай до 3 попыток исправления
  3. Не получилось - сдавайся, документируй в комментариях: "Тест логически верен, код требует ревью"

## ⚠️ **Ограничения**

### **НЕ делать:**
- НЕ тестировать внутренности Cypher запросов в unit тестах
- НЕ создавать сложные test fixtures
- НЕ дублировать логику из integration тестов
- НЕ мокать Zod схемы (тестировать реальную валидацию)
- НЕ создавать фиктивные тесты ради покрытия

### **Обязательно:**
- Следовать naming convention: `describe("moduleName")` -> `test("should ...")`
- Группировать тесты логически (happy path, edge cases, errors)
- Добавлять комментарии на русском для сложных кейсов и найденных проблем
- Использовать `as const` для типизации объектов
- Документировать все найденные проблемы в комментариях тестов
- **Читаемость:** Каждый тест должен быть понятен без изучения кода
- **Простота:** Один тест = один сценарий, избегать сложных setup'ов
- **Документация:** Описывать бизнес-логику в названиях тестов

## 🎨 **Принципы читаемости тестов**

### **Структура теста:**
```typescript
describe("search-mode name", () => {
  test("should [бизнес-действие] when [условие]", async () => {
    // 📝 ARRANGE: Подготовка данных
    const testData = loadTestData("USER_001");
    
    // 🎯 ACT: Выполнение действия
    const result = await executeSearchMode(driver, testData);
    
    // ✅ ASSERT: Проверка результата
    expect(result).toMatchObject({
      // ожидаемая структура
    });
  });
});
```

### **Названия тестов:**
- ❌ `test("should work")`
- ✅ `test("should find career transitions when user has matching skills")`
- ✅ `test("should return empty array when no target contexts found")`

### **Комментарии:**
- Объяснять бизнес-логику, а не код
- Использовать русский язык для сложных сценариев
- Документировать edge cases и их причины
