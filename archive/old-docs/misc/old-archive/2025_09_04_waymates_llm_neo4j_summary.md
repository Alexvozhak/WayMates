## 1) Решения, зафиксированные в этом чате

- **LLM‑выбор (на сейчас):**
  - **Qwen2.5‑7B‑Instruct** — основной кандидат для MVP (RU/EN, стабильный JSON, низкая цена).
  - **DeepSeek‑R1‑Distill‑Llama‑8B** — опционально для задач с повышенным reasoning (дешёвый на OpenRouter).
  - **Vikhr‑Nemo‑12B‑Instruct** — сильный RU + RAG‑режим, но рационально только как dedicated (дорого постоянно держать).
- **Контекст окна:** для нашего GraphRAG достаточно **~2k–3k токенов** на запрос; 32k хватает с большим запасом.
- **JSON‑требования к модели:** «JSON‑mode / structured output», стабильный формат при low‑temp; tool‑calling опционален.
- **Запись в Neo4j (GraphRAG):** записываем **только через наш маппер** в бэкенде. LLM и клиенты не пишут напрямую в БД.
- **APOC:** откладываем (не для боевого ingest). Использовать только для разовых/массовых импортов или миграций.
- **GraphQL:** откладываем. Если появятся внешние интеграции — ставим **ingest‑gateway** (REST/GraphQL) **перед** валидацией и маппером (а не прямой доступ к БД).
- **OGM:** опция на потом для **админских CRUD‑операций** (быстрые формы/правки); сложные GraphRAG‑чтения делаем низкоуровнево.
- **Конструктор запросов:** берём **`@neo4j/cypher-builder`** (официальный). Базовый слой — `neo4j-driver`.  
  Никаких конкатенаций строк; всё — параметризованно, через builder.

## 2) Контекст: сколько нам реально нужно

- системные инструкции: **300–500**
- вопрос пользователя: **50–150**

**Итого:** вход ≈ **1.2k–2.5k** токенов, выход ≈ **0.4k–0.8k**.  
**Вывод:** 32k окна достаточно; 128k — «запас», но не требование.

## 4) Что нам нужно от LLM по JSON

- Чистый **JSON‑ответ** (без лишнего текста), совместимый с нашей **JSON‑схемой** (TypeBox/AJV).  
- **Низкая температура** (t≈0.1–0.3), чтобы не «ломать» формат.  
- **Tool/Function calling** — опционально (полезно, но не критично для MVP, т.к. валидация и так на нашей стороне).

## 5) Запись в Neo4j — кто и как это делает

- Пишет **наш бэкенд‑маппер** (семантическая логика маппинга JSON → узлы/связи).  
- **LLM не пишет** в БД напрямую.  
- Параметризованные запросы формируем через **`@neo4j/cypher-builder`** → `build()` → `neo4j-driver.run(text, params)`.
- Валидация перед записью: **TypeBox/AJV** + семантические проверки (guards).

**Мини‑эскиз на builder (идея):**
```ts
const A = new Cypher.Node({ labels: ["AuthorStory"] });
const K = new Cypher.Node({ labels: ["Skill"] });
const p = {
  id: new Cypher.Param(s.id),
  title: new Cypher.Param(s.title),
  lang: new Cypher.Param(s.lang),
  skills: new Cypher.Param(s.skills),
};
const skillVar = new Cypher.Variable();
const q = Cypher.concat(
  Cypher.merge(A, { id: p.id }),
  Cypher.set(A, { title: p.title, lang: p.lang }),
  new Cypher.Unwind(p.skills, skillVar),
  Cypher.merge(K, { name: skillVar }),
  Cypher.merge(new Cypher.Relationship({ source: A, target: K, type: "HAS_SKILL" }))
);
// const { cypher, params } = q.build(); session.run(cypher, params);
```

## 6) APOC / GraphQL / OGM — позиция и применение

- **APOC** — отложено. Использовать **только** для разовых batch‑импортов/миграций внутри БД (не для боевого ingest).
- **GraphQL** — отложено. Если появятся партнёры/мультиклиентность, поднимем **ingest‑gateway** (REST/GraphQL) **до** маппера и валидаций; прямых записей в БД извне не будет.
- **OGM** — опционально для **админских CRUD‑панелей** (быстрее разработка, легче онбординг). Для сложных GraphRAG‑чтений остаёмся на низком уровне (builder/raw).

---

## 7) Чек‑лист внедрения

1. **Подключить** `@neo4j/cypher-builder` и `neo4j-driver`.  
2. **Создать индексы/уникальные ограничения** (напр., `AuthorStory.id`, `Skill.name`).  
3. **Оформить репозитории** (builder → `build()` → driver).  
4. **Валидация входа**: TypeBox/AJV + семантические guards.  
5. **Транзакции/батчи**: `session.executeWrite`, `UNWIND`, разумные размеры партий.  
6. **Логи/метрики**: время, размер батча, маскирование параметров.  
7. **Отложенные опции**: APOC‑playbook для импортов; ingest‑gateway (REST/GraphQL) при появлении внешних интеграций; OGM для админки.
