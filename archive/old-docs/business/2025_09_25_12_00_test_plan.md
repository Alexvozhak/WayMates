# Тестплан для WayMates

## Введение
Тестплан покрывает core компоненты: импорт (persist.ts), поиск (search_cohort_simple.ts), scoring и AutoTune. 

**Ключевая идея:** переиспользуем готовые данные вместо создания отдельных фикстур:
- **100 контекстов:** `data/contexts/generated/` — реальные разнообразные данные
- **10 запросов:** `data/contexts/generated/queries/` — готовые q1.json-q10.json  
- **Gold standard:** `data/gold/gold_labels.json` — ожидаемые результаты

**Инструменты:** Vitest + существующие npm скрипты (`import-batch`, `search-batch`)  
**Стратегия:** Minimal subset (3 контекста) для быстрых тестов, Full dataset (100) для E2E  
**Статусы:** ✅ = Выполнено, ❌ = Не выполнено (обновляется при реализации каждого теста)

### gold.helper.ts
```typescript  
export class GoldStandardChecker {
  static checkAccuracy(queryId: string, results: CohortMatch[]) {
    const gold = TestDataHelper.getGoldStandard();
    const expected = gold[queryId]?.gold_ids || [];
    const actual = results.map(r => extractUserId(r.context));
    
    return {
      precision: calculatePrecision(expected, actual),
      recall: calculateRecall(expected, actual), 
      f1: calculateF1(expected, actual)
    };
  }
}
```

## Уроки из реализации (09.25.2025)

### ❌ Ошибки при написании scoring unit тестов:

1. **Unit vs Integration confusion**
   - ❌ Делал: Тесты зависели от `DEFAULT_SCORING_WEIGHTS` из продакшн конфига
   - ✅ Правильно: Unit тесты должны быть изолированы с собственными `TEST_WEIGHTS`
   - **Урок:** Unit = чистая математика, Integration = связь компонентов

2. **Дублирование констант**
   - ❌ Делал: Создавал объект `weights` в каждом тесте отдельно
   - ✅ Правильно: Централизованные `TEST_WEIGHTS` на уровне файла
   - **Урок:** DRY принцип применяется и к тестовым данным

3. **Magic numbers в формулах**
   - ❌ Делал: `const expected = 3 * 0.5 + 0.6 * 0.2 + ...` (хардкод чисел)
   - ✅ Правильно: `const expected = 3 * TEST_WEIGHTS.matchedSkills + ...` (ссылки)
   - **Урок:** Тесты тоже должны быть maintainable

4. **Literal types проблема**
   - ❌ Делал: `export type ScoringWeights = typeof DEFAULT_SCORING_WEIGHTS` (as const)
   - ✅ Правильно: `export interface ScoringWeights { matchedSkills: number; ... }`
   - **Урок:** Слишком жесткие типы мешают тестированию

5. **Неактуальные комментарии**
   - ❌ Делал: `// Expected: 3*0.5 + ... = 1.82` (станут неактуальными)
   - ✅ Правильно: Код должен быть самодокументированным
   - **Урок:** Комментарии с расчетами быстро устаревают

6. **Confusion между входными данными и весами**
   - ❌ Путал: `ScoringInput` (результаты поиска) vs `ScoringWeights` (коэффициенты)
   - ✅ Понимание: Input = что нашли, Weights = насколько важно
   - **Урок:** Четко разделять domain entities

7. **Unsafe type casting для внешних данных**
   - ❌ Делал: `const q1Query = q1Json as QueryFile` (небезопасное приведение)
   - ✅ Правильно: `if (!isTypeOfTB(q1Json, QueryFileSchema)) throw Error(...)` (runtime валидация)
   - **Урок:** Внешние данные (JSON, API) должны валидироваться в runtime

### 📝 Правила для будущих unit тестов:

1. **Независимость:** Unit тесты не должны зависеть от продакшн конфигов
2. **DRY:** Централизовать тестовые данные на уровне файла/модуля  
3. **Maintainability:** Использовать ссылки на константы, избегать magic numbers
4. **Flexible types:** Интерфейсы лучше literal types для тестирования
5. **Self-documenting:** Код важнее комментариев с расчетами
6. **Clear separation:** Четко разграничивать domain entities и их назначение
7. **Track progress:** Отмечать выполненные тесты статусом ✅/❌ для видимости прогресса
8. **Runtime type safety:** Использовать `isTypeOfTB()` вместо `as Type` для валидации внешних данных
