# Оценка сроков освоения навыка по темпу — спецификация (MVP)

## 1) Цель системы
Давать честный ответ: **сколько недель** займёт навык при **выбранном пользователем темпе**. Если темп уже встречался — берём готовые числа; если новый — считаем оценку.

## 2) Поля `Skill` (минимум)
- `id`, `name`, **`tier` (звено 0/1/2)** — используется **только для холодного старта**.
- `gate` — *гейт‑навык*, «проходной пункт» для роли; **не занижаем** время и **не схлопываем** в родителя.
- `paradigm` — *парадигма*, новая модель мышления (например, FRP/RxJS, event‑sourcing, GraphQL schema‑first); при **первой встрече у пользователя** добавляем **надбавку ко времени**.

## 3) `TempoBucket` (темп‑шаблон)
Описание расписания: «сеанс X ч, Y раз/нед, пауза Z дней» + статистика: **обычно** (часы), **с запасом** (часы), **эффективность** расписания.  
Шаблон заносим в БД **только после фактического завершения** навыка по такому темпу.

## 4) Что ещё храним
- **`BaseEffortHoursByTier` (личное):** базовые «идеальные» часы пользователя по каждому звену (для холодного старта).
- **`UserFactor` (один на пользователя):** общий множитель скорости (старт = 1.0; обновляется по фактам).
- **`StudySessions`:** журнал сессий: дата, длительность (часы), пауза до сессии (дни), тип активности (курс/код/тест), источник (`live`/`memory`).

## 5) Роль звена (tier) — только холодный старт
Если по навыку **нет** темп‑шаблонов и **нет** живых данных, берём личные грубые оценки по **другим навыкам того же звена** как стартовый `BaseEffortHoursByTier`.

## 6) Расчёт сроков (две ветки)
**A. Темп совпал с темп‑шаблоном навыка.**  
- «Недели (обычно)» = (**часы_обычно × `UserFactor`**) / (**ваши часов/нед**).  
- «Недели (с запасом)» = (**часы_запас × `UserFactor`**) / (**ваши часов/нед**).  
- Дополнительно: если `gate = true` — не уменьшаем оценку; если `paradigm` новая для пользователя — добавляем надбавку.

**B. Темп новый.**  
- Оцениваем **эффективность расписания**: короткие сеансы — лучше; слишком длинные — штраф; «правильные» паузы — бонус.  
- «Недели» = (**`BaseEffortHoursByTier` × `UserFactor` × надбавка_за_paradigm?**) / (**ваши часов/нед × эффективность**).  
- Новый темп **не** записываем как шаблон до фактического завершения навыка.

## 7) Обновления после факта
Сравниваем прогноз и реальные часы → обновляем **`UserFactor`**; уточняем **`BaseEffortHoursByTier`**; создаём/обновляем **`TempoBucket`** для навыка (подтверждённый); **`StudySessions`** остаются в журнале.

## 8) Контекст про «квантили»
Они нужны, чтобы устойчиво получать две пользовательские цифры — **«обычно»** и **«с запасом»** — без влияния редких выбросов в данных. Внутри это опирается на позиционные границы распределения («середина» и «надежный запас»), но пользователю показываем именно «обычно / с запасом», без математических терминов.

## 9) Хранилище и стек
- **ClickHouse (OLAP):** основная аналитическая БД для длинных лент сессий, расчёта «обычно/запас» и эффективности.
- **Nest.js:** API (оценка по темпу, запись фактов).
- **n8n:** ETL и фоновые пересчёты.
- **LightRAG:** тексты/ресурсы/подсказки (не для статистики).

## 10) Итог‑правило (в одну строку)
**Темп есть →** берём «обычно/запас» из темп‑шаблона × `UserFactor` (с оглядкой на `gate/paradigm`).  
**Темп новый →** эффективность расписания × личный базис по звену × `UserFactor` (+ надбавка за новую парадигму; осторожность для `gate`).  
**После факта →** обновляем множитель и добавляем темп‑шаблон.
