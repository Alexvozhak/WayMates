## Рефлексия (сквозная)

### Как делать правильно
- **Семантические описания в промптах:** ЧТО + ПОЧЕМУ, не примеры фраз (guidelines.md §1.1)
- **Один источник правды:** buildHints() в DictionariesService, не дублировать в nodes
- **Wrapper pattern:** DictionariesService(cache) — бизнес-логика отдельно от кэширования
- **Dependency injection:** Normalizer(dictionaryCache) — минимальная зависимость
- **Полные названия:** sessionService, не session; documentaryService, не documentary
- **Константы вверху файла:** DICTIONARY_LABELS, не внутри метода
- **lint:fix часто:** Проверять после каждого логического блока изменений
- **Проверять внешние API при переименовании:** storedGoal в state ≠ existingGoal в chart API
- **replace_all с осторожностью:** Может затронуть параметры API с тем же именем

### Как делать неправильно
- **Примеры фраз в промптах:** LLM начинает pattern matching вместо понимания
- **sed без проверки:** Сломал import path (normalizer.js → normalizerService.js)
- **Смешивание ответственностей:** DictionariesCache с buildHints() = неправильное имя
- **Сокращённые имена:** dicts, cache, documentary — неявно, сложнее читать
- **Хардкод плюрализации:** `type + "S"` → INDUSTRYS вместо INDUSTRIES
- **Переименование без анализа семантики:** extractedGoal → targetContext не добавляет ясности

### Инсайты

1. **Wrapper pattern для separation of concerns:**
   - Cache = Redis operations (низкоуровневый)
   - Service = бизнес-логика (buildHints, форматирование)
   - Consumer выбирает нужный уровень абстракции

2. **Dependency injection через конструктор:**
   - Normalizer(dictionaryCache) — не знает о DictionariesService
   - Тестировать проще — можно мокать только нужное

3. **Naming consistency:**
   - `*Service` suffix для классов с бизнес-логикой
   - `*Cache` suffix для низкоуровневого кэширования
   - Полные имена переменных = self-documenting code

4. **sed опасен для массовых замен:**
   - Может сломать import paths
   - Может заменить внутри строк/комментариев
   - Лучше использовать replace_all в Edit tool

5. **`varName: TypeName` — стандартный TypeScript паттерн:**
   - `goal: Goal`, `session: Session` — нормально
   - Но переименование должно добавлять семантическую ясность

6. **Различай бизнес-логику state fields:**
   - `storedGoal` = Goal объект из БД (goalId, targetCriteria, timestamps)
   - `extractedGoal` = рабочий TargetContext (может быть не сохранён)
   - Переименование в `targetContext` не объясняет эту разницу

7. **filesystem MCP эффективнее для batch операций:**
   - `search_files` + `read_multiple_files` за один вызов
   - Вместо 10 отдельных Read + Edit

## Фаза 6: FEAT-040 Phase 6 (enrichResponse analysis) — решение принято

### Контекст проблемы

`enrichResponse` — async wrapper который добавляет в response:
- `availableFilters.reasons` — какие фильтры доступны (async из cache)
- `currentFilters.contextFields` — какие поля можно исключить (static enum)

### Глубокий анализ

**Два режима Facade:**

| Режим | Tool | Вход | Выход |
|-------|------|------|-------|
| NLP | `converse` | message (текст) | `{ message, result }` |
| API | `search-careers` | structured params | `ScoredMatchedCandidate[]` |

**Ключевые находки:**
1. `search-careers` вызывает Core API напрямую, НЕ проходит через SearchGraph
2. `enrichResponse` используется ТОЛЬКО в converse flow
3. NlpFormatter получает `result` и форматирует в текст
4. `availableFilters` — overhead для NLP mode (пользователь пишет текст, не выбирает из dropdown)

**Available vs Applied:**
- `availableFilters` / `currentFilters` — что МОЖНО выбрать (не нужно для NLP)
- `appliedFilters` / `appliedCurrentFilters` — что БЫЛО применено + rejected (нужно для feedback)

### Решение

**Убрать `enrichResponse` и упростить response:**
1. Удалить `availableFilters`, `currentFilters` из SearchGraphResponse schema
2. Удалить `enrichResponse` функцию из search-graph.ts
3. Оставить `appliedFilters`, `appliedCurrentFilters` — feedback о применённых фильтрах
4. response-builders возвращают только dynamic state data (без null полей)

### Обоснование

- NLP клиенты не используют `availableFilters` (им нужен только `message`)
- Rich UI клиенты должны использовать API mode (`search-careers`) с известной схемой
- Hybrid UI (NLP + dropdowns) — антипаттерн: знаешь структуру → используй API, не NLP
