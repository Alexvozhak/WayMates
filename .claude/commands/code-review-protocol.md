# Code Review Protocol

## Когда пользователь спрашивает "смущает код?" / "есть проблемы?" / "можно улучшить?"

### 1. СНАЧАЛА: Что работает ПРАВИЛЬНО
- Назови корректные паттерны и объясни ЗАЧЕМ они нужны
- Не перескакивай к проблемам

### 2. ПРОВЕРКА "ВЕЛОСИПЕДА"

#### A. Проверить package.json
```bash
grep "library_name\|similar" package.json
```

**Правило**: Если подходящая либа УЖЕ установлена → изучить её API (context7) перед предложением альтернативы.

**Примеры:**
- Предлагаю retry либу → проверить: может SDK имеет встроенный?
- Предлагаю HTTP клиент → проверить: есть ли axios/fetch/SDK transport?
- Предлагаю валидатор → проверить: есть ли zod/yup?
- Предлагаю парсер → проверить: есть ли встроенный в либе?

**Правило**: Если установленная либа решает ≥90% задачи → НЕ предлагать аналог

#### B. Есть ли встроенное решение?
```
[ ] Проверил документацию библиотеки (context7/WebFetch)
[ ] Есть ли встроенный метод SDK?
[ ] Может native JS достаточно?
```

#### C. Используем ли правильно?
```
[ ] Изучил API (context7) - может есть лучший метод?
[ ] Может используем устаревший способ?
```

### 3. ИЗВЕСТНЫЕ ПАТТЕРНЫ (БЕЗ оверинженеринга)

**Проверить соответствие задачи паттерну:**

| Задача | Паттерн | Когда НЕ применять |
|--------|---------|-------------------|
| Изоляция внешних API | Adapter | Если API простой (1-2 метода) |
| Выбор реализации runtime | Strategy | Если вариант один |
| Создание сложных объектов | Builder | Если <5 параметров |
| Ленивая инициализация | Singleton | Если объект дешевый |
| Валидация цепочкой | Pipeline | Если <3 шагов |

**Checklist перед применением паттерна:**
```
[ ] Упрощает ли код? (меньше строк, понятнее)
[ ] Решает РЕАЛЬНУЮ проблему? (не "может пригодиться")
[ ] Не усложняет простые сценарии?
```

### 4. ФАКТЫ о проблемах (если есть)

✅ **Это проблемы:**
- Unused код (`grep usage` → 0 результатов)
- Дублирование (одинаковый код в ≥2 местах)
- Баги (runtime errors, logic bugs, type errors)
- Изобретение велосипеда (есть встроенное/установленное решение)
- Нарушение конвенций проекта (CLAUDE.md, eslint)
- Performance bottleneck (профилирование показало)

❌ **Это НЕ проблемы:**
- "Можно иначе" (без улучшения метрик)
- "Давайте упростим" (без фактов)
- "Вот альтернативный подход" (без обоснования)
- Применение паттерна "на будущее"

### 5. Checklist ПЕРЕД предложением

```
Мое предложение улучшает:
[ ] Читаемость? (меньше строк / понятнее naming)
[ ] Производительность? (меньше вычислений - измеримо)
[ ] Убирает дублирование? (факт: код в ≥2 местах)
[ ] Убирает рудименты? (факт: unused код)
[ ] Использует готовое решение? (проверил package.json)
[ ] Применяет паттерн БЕЗ усложнения?
[ ] Следует best practices? (проверил в docs via context7)

Если < 2 галочек → НЕ ПРЕДЛАГАТЬ
```

### 6. Проверка API библиотеки ОБЯЗАТЕЛЬНА

- Не уверен в API? → `context7` или `WebFetch` документация
- Предлагаю альтернативу? → проверить что она существует
- Изобретаем велосипед? → проверить встроенные возможности

### 7. "Код нормальный" - ВАЛИДНЫЙ ответ

- Если только 1 мелкий рудимент → так и скажи
- НЕ ищи проблемы для "полноты ответа"
- НЕ применяй паттерны "на будущее"
- НЕ предлагай "можно иначе" без фактов

## Формат ответа

```markdown
### ✅ Что работает правильно
- Паттерн X оправдан, потому что Y
- Валидация правильная, защищает от Z

### ❌ Факты о проблемах (если есть)
- `_timeoutMs` unused (проверил grep → 0 usage)
- Дублирование в file1.ts:10 и file2.ts:25

### 🔍 Проверка велосипеда
- Проверил package.json → есть `zod`
- Проверил SDK docs → нет встроенного retry

### 💡 Рекомендации (если есть)
- Убрать `_timeoutMs` - рудимент
- Использовать `zod` вместо ручной валидации
```

## Примеры

### ❌ ПЛОХО (предлагаю без фактов)
```
"Давайте упростим parseJsonContent - можно короче"
"Wrapper не нужен, вот альтернатива..."
"Применим Strategy pattern для будущего расширения"
```

### ✅ ХОРОШО (факты + проверки)
```
"✅ Код правильный:
- Wrapper типизирует tool names → защита от опечаток
- parseJsonContent с проверками → защита от runtime errors

❌ Один рудимент:
- `_timeoutMs` unused (grep показал 0 usage)

Рекомендация: убрать `_timeoutMs`"
```

## 8. После анализа → AskUserQuestion с исправлениями

**Обязательно**: Группируй исправления по категориям, каждая = отдельный вопрос:
- **Bugs fix** - критичные баги (multiSelect: true)
- **Simplify** - убрать избыточность (multiSelect: true)
- **Improvements** - экспорты, типы (multiSelect: false для да/нет)

**В description**: конкретные факты (строки, метрики, доказательства)

**Пример**:
```typescript
{
  question: "Какие критичные баги исправить?",
  header: "Bugs fix",
  multiSelect: true,
  options: [
    {
      label: "Pathname bug (line 63)",
      description: "Добавить !url.pathname. БАГ: new URL('http://localhost:3001').pathname === '' не обрабатывается"
    }
  ]
}
```

**Исключение**: Если 0 проблем → ответ "Код правильный"
