# Наставления

Документ описывает общий стиль и подход к работе в проекте WayMates. Каждое наставление проработано до первопричины — лечим не симптомы, а ставим диагноз.

**Как использовать**: При `/before-rewind` сверяться с этим документом, добавлять новые инсайты из сессии, не дублировать существующие.

## 1. LLM Prompts

### 1.1 Примеры в промптах

| | |
|---|---|
| **Паттерн ошибки** | Добавляю дословные примеры в промпты для extraction/classification |
| **Первопричина** | Сам обучался few-shot, думаю что примеры помогут. Но: (1) LLM начинает pattern matching вместо понимания смысла, (2) зацикливается на примерах и не генерализирует на новые случаи |
| **Правило** | Семантические описания: описывай ЧТО искать и ПОЧЕМУ, не КАК выглядит конкретная фраза |

### 1.2 Словари для extraction

| | |
|---|---|
| **Паттерн ошибки** | Не инжектирую словари в extraction промпты |
| **Первопричина** | Не понимаю что LLM не знает канонические значения проекта и будет выдумывать ("Information Technology" вместо "backend") |
| **Правило** | Словари = source of truth. Инжектировать position, domain, skill, industry в промпт. LLM сопоставляет семантически |

### 1.3 Multilingual input

| | |
|---|---|
| **Паттерн ошибки** | Забываю указать что input может быть на любом языке |
| **Первопричина** | Промпт на английском → LLM ожидает английский input |
| **Правило** | "Response may be in any language" — обязательно для русского/смешанного input |

### 1.4 Контекст диалога для classification

| | |
|---|---|
| **Паттерн ошибки** | Парсер интента получает только message, не знает phase |
| **Первопричина** | Думаю что intent универсален. Но "хочу senior" = разный intent в разных фазах |
| **Правило** | Передавать phase context в classifier — что бот спросил определяет смысл ответа |

## 2. Tests

### 2.1 Подгонка assertion под код

| | |
|---|---|
| **Паттерн ошибки** | Тест падает → меняю assertion чтобы прошёл |
| **Первопричина** | Хочу быстрый "зелёный" результат. Но: (1) тест = бизнес-требование, (2) меняя assertion — теряю защиту от регрессии, (3) пропускаю потенциальный баг в бизнес-коде |
| **Правило** | Тест падает → исследуй ПОЧЕМУ → часто это баг в бизнес-коде. Цель тестов — выявить баги, не поднять coverage |

### 2.2 Театральные проверки

| | |
|---|---|
| **Паттерн ошибки** | Пишу бессмысленные assertions типа `expect(x).toBeGreaterThanOrEqual(0)` |
| **Первопричина** | Coverage theater — хочу показать что "протестировано" |
| **Правило** | Тесты проверяют бизнес-инварианты. Если assertion не может упасть на реальном баге — он бесполезен |

### 2.3 Graceful handling для edge cases

| | |
|---|---|
| **Паттерн ошибки** | Для gibberish/unknown input проверяю конкретный LLM output |
| **Первопричина** | Думаю что LLM предсказуем. Но LLM непредсказуем с edge cases |
| **Правило** | Проверяй инварианты системы (не упала, фаза валидна), не конкретный output |

### 2.4 Фикстуры с актуальными датами

| | |
|---|---|
| **Паттерн ошибки** | Создаю фикстуры с датами 2022 года |
| **Первопричина** | Не думаю о production thresholds (recency filter = 12 месяцев) |
| **Правило** | Даты в фикстурах должны быть в пределах production thresholds |

### 2.5 Логика тестовых данных

| | |
|---|---|
| **Паттерн ошибки** | User достигает цели раньше Pathfinder в тестовых данных |
| **Первопричина** | Генерирую данные без проверки бизнес-логики |
| **Правило** | Всегда проверять что тестовые данные имеют смысл в бизнес-контексте |

### 2.6 Negative assertions

| | |
|---|---|
| **Паттерн ошибки** | Тест проверяет только "U5 найден" без проверки "U8 НЕ найден" |
| **Первопричина** | Фокус на happy path |
| **Правило** | Проверять что правильное найдено + что неправильное исключено |

## 3. Types/Zod

### 3.1 Смешивание null/undefined

| | |
|---|---|
| **Паттерн ошибки** | Использую то null, то undefined для "отсутствия значения" |
| **Первопричина** | В JS оба значат "отсутствие". Но: (1) OpenAI structured output требует nullable, не optional, (2) Neo4j возвращает null для отсутствующих полей, (3) JSON не имеет undefined |
| **Правило** | `null` единообразно. Один способ = один источник истины |

### 3.2 Касты `as Type`

| | |
|---|---|
| **Паттерн ошибки** | Использую `as Type` чтобы "заткнуть" TypeScript |
| **Первопричина** | Быстрее чем исправить типы |
| **Правило** | Каст = сигнал что типы неправильные. Использовать: (1) Zod `.parse()` — предпочтительно, (2) самописный typeguard — на крайняк |

### 3.3 Weak typing для LLM schemas

| | |
|---|---|
| **Паттерн ошибки** | `z.array(z.string())` для полей с ограниченным набором значений |
| **Первопричина** | Быстрее написать string чем enum |
| **Правило** | `z.array(z.enum([...]))` — LLM видит допустимые значения в JSON schema |

## 4. Код и паттерны

### 4.1 Фаллбэки и врапперы "на всякий случай"

| | |
|---|---|
| **Паттерн ошибки** | Добавляю factory helpers, fallback values, wrapper objects без явной необходимости |
| **Первопричина** | Хочу "безопасность" и "расширяемость". Но: (1) засоряет бизнес-код, (2) глотает ошибки вместо всплытия, (3) прячет реальное поведение глубоко в абстракции |
| **Правило** | YAGNI. Добавляй сложность только когда есть доказанная необходимость |

### 4.2 Хардкод значений

| | |
|---|---|
| **Паттерн ошибки** | Хардкожу levels, options, значения вместо получения из источника |
| **Первопричина** | Быстрее написать константу |
| **Правило** | Данные из источника: словари из БД, levels из trajectories, config из env |

### 4.3 Дублирование vs DRY

| | |
|---|---|
| **Паттерн ошибки** | Вижу дублирование → откладываю "на потом" |
| **Первопричина** | Хочу быстрее закончить текущую задачу |
| **Правило** | Видишь дублирование → HOF/abstraction сразу. 1 час на HOF = экономия на поддержке |

### 4.4 Inline "грязь"

| | |
|---|---|
| **Паттерн ошибки** | `...(condition && { field })` inline в return |
| **Первопричина** | Компактнее |
| **Правило** | Явные переменные или if/else для читаемости. Код читают чаще чем пишут |

### 4.5 Сложные условия

| | |
|---|---|
| **Паттерн ошибки** | `if (a && b.length > 0 && c !== "x")` без именования |
| **Первопричина** | Кажется очевидным |
| **Правило** | Complex conditions → named variables: `const hasData = ...; const shouldRun = ...;` |

### 4.6 Имя не соответствует семантике

| | |
|---|---|
| **Паттерн ошибки** | Функция меняет поведение, имя остаётся старым (`createSystemMessage` когда уже не system message) |
| **Первопричина** | Имя — "просто строка", не часть контракта. Но: (1) имя = документация для следующего читателя, (2) неверное имя = ложные ожидания = баги |
| **Правило** | Семантика меняется → имя меняется. Имя — часть контракта |

### 4.7 Ручная работа вместо инструментов

| | |
|---|---|
| **Паттерн ошибки** | Ручной cleanup импортов, форматирование, сортировка |
| **Первопричина** | Не знаю/забываю о возможностях инструментов |
| **Правило** | `lint:fix` удаляет unused imports, форматирует код. Инструменты автоматизируют рутину — использовать их |

## 5. LangGraph

### 5.1 userResponse не очищается

| | |
|---|---|
| **Паттерн ошибки** | Использую userResponse но не очищаю для следующего node |
| **Первопричина** | Не помню что state reducer `lastValue` сохраняет значения между вызовами. `"" || interrupt()` всегда вызовет interrupt |
| **Правило** | После использования userResponse → `userResponse: ""` в return (кроме случаев когда следующий node должен его получить) |

### 5.2 buildRouteMap не содержит все destinations

| | |
|---|---|
| **Паттерн ошибки** | Routing function возвращает node которого нет в buildRouteMap |
| **Первопричина** | Не проверяю все return values роутера |
| **Правило** | `buildRouteMap destinations === ВСЕ возможные return values` из routing функции |

### 5.3 unknown intent без явного handling

| | |
|---|---|
| **Паттерн ошибки** | Полагаюсь на fallback `??` для unknown intent |
| **Первопричина** | Думаю что LLM всегда вернёт валидный intent |
| **Правило** | Explicit route для `unknown` → `clarify_intent` node. LLM должна иметь путь отступления |

### 5.4 Debug логи в production коде

| | |
|---|---|
| **Паттерн ошибки** | Добавляю console.log для отладки и забываю удалить |
| **Первопричина** | Тороплюсь исправить баг |
| **Правило** | Debug логи — временные. Добавил → понял → удалил. Для production есть Pino + LangSmith |

### 5.5 Intent добавлен в routing, но не в schema

| | |
|---|---|
| **Паттерн ошибки** | Добавляю новый intent в routing, но забываю добавить в Zod schema и prompt |
| **Первопричина** | Не понимаю что intent проходит через ТРИ слоя: schema → prompt → routing |
| **Правило** | При добавлении intent — проверить ВСЕ 4 места: (1) `state.ts` — SIMPLE_INTENTS/COMPLEX_INTENTS, (2) `parse-intent.ts` — Zod schema, (3) `prompts.ts` — INTENT_DESCRIPTIONS + PHASE_CONTEXT, (4) `search-router.ts` — routing |

### 5.6 Hardcoded строки в промптах

| | |
|---|---|
| **Паттерн ошибки** | Intent names в промпте как строки ("PROCEED", "CLARIFY"), не связаны с enum |
| **Первопричина** | Быстрее написать строку чем сделать type-safe |
| **Правило** | Single source of truth: enum в `state.ts`, промпт интерполирует через `Record<EnumType, string>`. TypeScript ловит рассинхрон на compile time |

### 5.7 Overwrite вместо Merge для incremental input

| | |
|---|---|
| **Паттерн ошибки** | При дополнении данных (adhoc context, goal) извлекаю заново с нуля, теряя уже собранное |
| **Первопричина** | Не думаю о multi-turn flow. Каждое сообщение обрабатываю изолированно |
| **Правило** | LLM merge pattern: передать текущее состояние в промпт (`Current: {json}`), LLM сама решает что обновить/сохранить. Пример: `buildAdhocClarificationPrompt`, `buildGoalClarificationPrompt` |

### 5.8 Placeholder strings вместо explicit arguments

| | |
|---|---|
| **Паттерн ошибки** | `PROMPT.replace("{field}", value)` — неявная подстановка |
| **Первопричина** | Быстрее написать placeholder чем продумать API функции |
| **Правило** | Builder function с явными аргументами: `buildPrompt(arg1, arg2)`. IDE подсказывает, TypeScript проверяет |

### 5.9 ask intent не добавлен во все фазы

| | |
|---|---|
| **Паттерн ошибки** | "что ты умеешь?" классифицируется как cancel |
| **Первопричина** | `ask` intent добавлен только в некоторые фазы PHASE_CONTEXT. В остальных LLM не имеет валидного варианта для мета-вопросов |
| **Правило** | `ask` intent должен быть в КАЖДОЙ фазе. Пользователь может задать мета-вопрос в любой момент |

### 5.13 Prompt показывает все intents, LLM игнорирует Valid constraint

| | |
|---|---|
| **Паттерн ошибки** | LLM выбирает semantically matching intent вместо Valid intent |
| **Первопричина** | Prompt содержит ALL intent descriptions + "Valid: X, Y". LLM делает semantic match, игнорирует constraint |
| **Правило** | Prompt должен показывать ТОЛЬКО valid intents. Router = source of truth. `getValidIntentsForPhase(phase, flags)` |

### 5.14 proceed ≠ explore (семантика)

| | |
|---|---|
| **Паттерн ошибки** | "глянь похожих" → proceed → wrong routing |
| **Первопричина** | `proceed` = "agrees WITHOUT new info". "глянь похожих" = новая информация (что хочет пользователь) |
| **Правило** | `proceed` = pure confirmation. `explore` = request to see similar people. Разные семантики |

### 5.10 Advisor как тупик без выхода

| | |
|---|---|
| **Паттерн ошибки** | Advisor имеет только `ask` и `done` интенты, нет выхода в main flow |
| **Первопричина** | Думаю что advisor — финальная точка. Но пользователь может захотеть действие (set goal, filter) из advisor |
| **Правило** | Generic `action` intent в advisor → роутит в parse_search_intent с сохранённым userResponse. Не дублировать интенты — main flow разберётся |

### 5.11 INTERRUPT ноды нельзя использовать как промежуточные

| | |
|---|---|
| **Паттерн ошибки** | Роучу из advisor в confirm_adhoc_context чтобы "вернуться в flow" |
| **Первопричина** | Не понимаю что interrupt() ВСЕГДА останавливает выполнение и ждёт ввода |
| **Правило** | Для возврата в flow без interrupt — роутить напрямую в PARSE ноду (parse_search_intent). Нужен previousPhase чтобы знать route map |

### 5.12 Инструкции одной фазы влияют на другие

| | |
|---|---|
| **Паттерн ошибки** | NLP для `confirming_adhoc_context` спрашивает seniority, хотя это инструкция для `asking_adhoc_context` |
| **Первопричина** | Все описания фаз в одном SEARCH_PROMPT. LLM видит все инструкции и может применить не ту |
| **Правило** | Инструкции в PHASE_DESCRIPTIONS должны быть взаимоисключающими. Не "Ask for X", а "DO NOT ask for anything from FILLED section" |

### 5.11 Manual type alias вместо keyof

| | |
|---|---|
| **Паттерн ошибки** | `type Field = "a" \| "b" \| "c"` дублирует ключи бизнес-типа |
| **Первопричина** | Копировал поля вручную, не думал о связи с бизнес-типом |
| **Правило** | `Record<keyof BusinessType, string>` — single source of truth. При добавлении поля в schema — TypeScript потребует описание |

## 6. Cypher/Neo4j

### 6.1 WITH clause scope

| | |
|---|---|
| **Паттерн ошибки** | Забываю что WITH сбрасывает переменные не в списке |
| **Первопричина** | Не помню семантику Cypher WITH |
| **Правило** | `WITH *` сохраняет все, `WITH x, y` — только x и y. Всегда проверять что нужные переменные пробрасываются |

### 6.2 Null safety для optional properties

| | |
|---|---|
| **Паттерн ошибки** | `WHERE all(d IN c.domains WHERE ...)` без проверки на null |
| **Первопричина** | Предполагаю что поля заполнены |
| **Правило** | `CASE WHEN x IS NULL THEN true ELSE ... END` для всех optional properties в WHERE |

### 6.3 Map projection вместо field mapping

| | |
|---|---|
| **Паттерн ошибки** | Маплю поля в TypeScript вместо Cypher |
| **Первопричина** | Привычка |
| **Правило** | `RETURN { field1, field2, computed: expr } AS result` — type conversions в Cypher, один cast в TypeScript |

### 6.4 LIMIT без GROUP BY

| | |
|---|---|
| **Паттерн ошибки** | `ORDER BY x LIMIT 1` после aggregation — возвращает 1 строку globally |
| **Первопричина** | Ожидаю per-group limit как в SQL |
| **Правило** | Для per-group limit: `collect(...)[0]` внутри aggregation, не LIMIT |

### 6.5 Debug сложных queries

| | |
|---|---|
| **Паттерн ошибки** | Debug всего query сразу, не понимаю где проблема |
| **Первопричина** | Не хочу тратить время на изоляцию |
| **Правило** | Убирай части query по одной, пока результат не изменится — найдёшь проблемную часть |

## 8. Коммуникация

### 8.1 Угодничество вместо анализа

| | |
|---|---|
| **Паттерн ошибки** | Подтверждаю ожидания пользователя вместо объективного анализа |
| **Первопричина** | Хочу угодить, избегаю конфликта. Но: (1) пользователь теряет возможность пересмотреть решение, (2) технический долг накапливается, (3) моя роль — экспертиза, не поддакивание |
| **Правило** | Честный анализ > подтверждение ожиданий. "Нужен ли MCP?" → анализ плюсов/минусов, не "да, конечно нужен!" |

| **Правило** | Объясняй как будто собеседник не знает контекст. "Печатаем JS в текстовый файл" понятнее чем "esbuild bundle injection" |

### 8.2 Не уточняю неоднозначности

| | |
|---|---|
| **Паттерн ошибки** | Делаю предположения вместо вопросов |
| **Первопричина** | Не хочу "надоедать" вопросами |

### 3.4 Добавление mode в discriminated union

| | |
|---|---|
| **Паттерн ошибки** | Добавил новый mode, но методы делают assumptions о структуре данных старых modes |
| **Первопричина** | Не проследил data flow — какие методы зависят от структуры `trajectories[0]` и т.п. |
| **Правило** | При добавлении mode — grep по всем методам класса/модуля, проверить каждый на assumptions о данных |
